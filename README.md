# Онлайн-бронирование столиков в ресторане

Веб-приложение для бронирования столиков: форма с валидацией, интерактивная схема зала с занятостью столиков и серверный API с хранением броней в Postgres (Neon). Деплой — на Vercel.

## Возможности

- **Форма бронирования** с проверкой полей:
  - имя (от 2 символов);
  - телефон с маской `+7 (XXX) XXX-XX-XX` и проверкой полного номера;
  - количество гостей (1–12), дата (не раньше сегодняшней, по локальному времени), время (прошедшие слоты выбрать нельзя);
  - обязательный чекбокс «С политикой конфиденциальности ознакомлен».
- **Интерактивная схема зала** (SVG) в модальном окне: 31 столик, статусы «свободен», «занят» и «мало мест для вашей компании». Выбор мышью, касанием и клавиатурой. Выбор столика необязателен: можно оставить «любой свободный», и сервер сам назначит подходящий.
- **Занятость зависит от даты, времени и числа гостей.** Если пользователь меняет их после выбора столика, выбор сбрасывается с пояснением.
- **Серверный API** проверяет данные, считает занятость и создаёт бронь. Двойная бронь одного столика исключена на уровне базы данных.
- **Экран подтверждения** с итогом и номером столика (даже если столик назначил сервер).
- **Доступность:** подписи к полям, `aria-invalid` и `aria-describedby` для ошибок, управление селектами и картой с клавиатуры, анимации отключаются при `prefers-reduced-motion`.
- **Адаптивность:** на телефоне окно выбора столика занимает весь экран, схема прокручивается по горизонтали.

## Структура проекта

Фронтенд организован по FSD (Feature-Sliced Design), серверная логика вынесена в отдельную папку `server`.

```
booking-restaurant/
├─ db/
│  └─ schema.sql                  # схема БД: выполнить один раз
├─ src/
│  ├─ entities/
│  │  └─ table/                   # сущность «столик»
│  │     ├─ api/                  #   запрос занятости
│  │     ├─ config/hallLayout.ts  #   схема зала и число мест (единый источник данных)
│  │     ├─ lib/                  #   расстановка стульев, склонение «места»
│  │     ├─ model/                #   типы, хук useTableAvailability
│  │     └─ ui/HallMap.tsx        #   SVG-карта зала
│  ├─ features/
│  │  └─ booking/                 # фича «бронирование»
│  │     ├─ api/submitBooking.ts  #   отправка брони на сервер
│  │     ├─ model/                #   типы, валидация, работа с датами, хук формы
│  │     └─ ui/                   #   BookingForm, TablePicker, ConfirmationScreen
│  ├─ shared/
│  │  ├─ config/constants.ts      # слоты времени, варианты гостей, ссылка на политику
│  │  ├─ lib/phoneMask.ts         # маска телефона
│  │  └─ ui/                      # CustomSelect, Modal, icons
│  ├─ server/                     # серверная логика (используется только в API)
│  │  ├─ bookingRepo.ts           #   работа с БД (Postgres или память)
│  │  ├─ bookingService.ts        #   создание брони, назначение столика
│  │  ├─ availability.ts          #   статусы столиков
│  │  ├─ occupancy.ts             #   модель загрузки зала
│  │  ├─ time.ts                  #   часовой пояс ресторана, окно брони
│  │  └─ validation.ts            #   проверка входящих данных
│  ├─ pages/
│  │  ├─ index.tsx                # главная страница
│  │  └─ api/
│  │     ├─ tables.ts             # GET  /api/tables
│  │     └─ bookings.ts           # POST /api/bookings
│  └─ styles/                     # глобальные стили и CSS-переменные
└─ README.md
```

Схема зала и вместимость столиков хранятся в одном месте: `src/entities/table/config/hallLayout.ts`. Из него берут данные и карта, и сервер.

## Быстрый старт

Нужен Node.js 20.9 или новее (минимум для Next.js 16).

```bash
git clone https://github.com/stephcurry270/booking-restaurant.git
cd booking-restaurant
npm install
npm run dev
```

Приложение откроется на http://localhost:3000.

**Без базы данных** локально всё работает: брони хранятся в памяти и пропадают при перезапуске сервера. Чтобы сохранять их по-настоящему, подключите Postgres (раздел ниже).

### Скрипты

| Команда | Что делает |
|---|---|
| `npm run dev` | dev-сервер |
| `npm run build` | продакшен-сборка (проверяет типы) |
| `npm run start` | запуск собранного приложения |
| `npm run lint` | проверка ESLint |
| `npm run lint:fix` | ESLint с автоисправлением |

В Next.js 16 команда `next lint` удалена, а `next build` больше не запускает линтер. Поэтому перед коммитом выполняйте `npm run lint` и `npm run build` отдельно.

## Переменные окружения

Локально их кладут в файл `.env.local` в корне проекта (он в `.gitignore` и не попадает в репозиторий). На Vercel — Settings → Environment Variables.

| Переменная | Обязательна | Назначение |
|---|---|---|
| `DATABASE_URL` | в продакшене — да | Строка подключения к Postgres. Без неё локально брони хранятся в памяти, а в продакшене сервер намеренно возвращает ошибку, чтобы брони не терялись молча |
| `RESTAURANT_TIME_ZONE` | нет | Часовой пояс ресторана, по умолчанию `Europe/Moscow`. Vercel работает в UTC, поэтому от этой переменной зависит, что считается «сегодня» |

Пример `.env.local`:

```
DATABASE_URL=postgres://user:password@host/dbname?sslmode=require
RESTAURANT_TIME_ZONE=Europe/Moscow
```

Никогда не коммитьте реальные значения. Если строка подключения попала в Git, смените пароль в Neon.

## База данных

1. Создайте базу Neon. Проще всего через Vercel: Storage → Neon (интеграция из Marketplace), затем подключите её к проекту. Vercel сам добавит `DATABASE_URL`.
2. Откройте Neon Console → SQL Editor, вставьте содержимое `db/schema.sql` и нажмите Run.
3. Для локальной работы скопируйте `DATABASE_URL` в `.env.local` и перезапустите `npm run dev`.

Таблица `bookings` содержит имя, телефон, число гостей, номер столика и время начала и конца брони. Ограничение `EXCLUDE` не позволяет создать две брони одного столика с пересекающимся временем, даже если два запроса пришли одновременно. Перечень столиков в базе не хранится: он берётся из `hallLayout.ts`.

## API

### `GET /api/tables?date=YYYY-MM-DD&time=HH:MM&guests=N`

Возвращает статус каждого столика на выбранное время.

```json
{
  "date": "2026-11-17",
  "time": "19:00",
  "guests": 4,
  "freeCount": 16,
  "tables": [{ "id": 1, "seats": 2, "status": "too_small" }]
}
```

Статусы: `free` (свободен), `busy` (занят), `too_small` (мест меньше, чем гостей).

### `POST /api/bookings`

Тело запроса:

```json
{
  "name": "Иван",
  "phone": "+7 (921) 047-71-77",
  "date": "2026-11-17",
  "time": "19:00",
  "guests": 4,
  "tableId": null
}
```

`tableId: null` означает «любой свободный»: сервер выберет самый маленький из подходящих столиков.

| Код | Когда |
|---|---|
| `201` | бронь создана: `{ id, tableId, startsAt }` |
| `400` | некорректные данные, прошедшее время, столик слишком мал или не существует |
| `405` | неверный HTTP-метод |
| `409` | `TABLE_TAKEN` (столик только что заняли) или `NO_TABLES` (свободных столиков нет) |
| `500` | внутренняя ошибка |

## Как считается занятость

Бронь занимает столик на 2 часа. Занятость складывается из двух слоёв:

1. **Реальные брони** из базы данных.
2. **Бета-модель загрузки зала** (`src/server/occupancy.ts`): вероятность занятости зависит от часа (пики в обед и вечером), дня недели (в выходные загруженнее) и того, насколько заранее смотрит гость. В часы пик в день визита свободных мест почти нет, а при записи заранее шансов найти столик больше. Результат для одного и того же запроса всегда одинаков, поэтому схема не «мерцает» при перезагрузке.

Все коэффициенты собраны в одном файле, их можно подкрутить под реальную загрузку ресторана. Когда появятся настоящие данные о посетителях, второй слой можно отключить.

## Деплой на Vercel

1. Подключите репозиторий к Vercel (Import Project). Настройки Next.js определятся автоматически.
2. Подключите Neon (см. «База данных») и убедитесь, что `DATABASE_URL` есть для окружений Production и Preview.
3. При необходимости добавьте `RESTAURANT_TIME_ZONE`.
4. Запушьте ветку: Vercel соберёт preview-деплой. Проверьте на нём весь сценарий: выбор даты и времени, карта, выбор столика, отправка, экран подтверждения.
5. Смержите ветку в `main`: Vercel выкатит продакшен.

После изменения переменных окружения нужен новый деплой: к уже собранным версиям они не применяются. Тестовые брони удаляйте перед боевым запуском: `delete from bookings;` в SQL Editor.

## Что можно улучшить

- Заменить заглушку `PRIVACY_POLICY_URL` в `src/shared/config/constants.ts` на реальную страницу политики конфиденциальности.
- Заменить прототип схемы зала на реальную планировку ресторана (`hallLayout.ts`).
- Добавить масштабирование схемы жестами (pinch-zoom) на телефонах.
- Подтверждение брони по SMS или e-mail и отмена брони.
- Тесты для валидации, работы с датами, маски телефона и серверной логики.
